# textlint-rule-preset-ja-no-ai-slop

日本語の文章で、不自然な言い回しを検出するtextlintプリセットです。指摘に理由と修正の方向性を内包させ、どのように改善するか示します。

## 使い方

```sh
npm install --save-dev textlint textlint-rule-preset-ja-no-ai-slop
```

`.textlintrc.json`に設定します。

```json
{
  "rules": {
    "preset-ja-no-ai-slop": true
  }
}
```

```sh
npx textlint article.md
```

指摘の規則IDは`ja-no-ai-slop/unspecified-behavior`のようにプリセット名を含みます。修正に必要な情報が文章から特定できない場合、その値を推測せずに確かめるための注意をメッセージに含めています。

## 対応範囲

各規則は、それぞれの説明に挙げた言葉や表現を含む文だけを検査します。

### literal-verb-translation

技術的な動作を説明する文で、「割る」「を置く」「を呼ぶ」「に／へ寄せる」「繋ぐ」を検出します。文脈によっては問題のない使い方もあるため、指摘のメッセージで対象と動作を確かめるよう案内します。

#### 検出される例

```markdown
レビューしやすいよう、変更したコードを二つのコミットに割って提出します。
差分を二つに割ったあと、それぞれのCIを実行します。
検証の入口をここに置きます。
失敗時にREADMEを呼びます。
baseline生成をCIに寄せます。
handlerを実装し、usecaseへ繋ぎました。
処理対象の値を表に置く手順を、設計書に記載します。
変更を一つのコミットに寄せる方針で、レビューを依頼します。
```

#### 検出されない例

```markdown
レビューしやすいよう、変更したコードを二つのコミットに分割して提出します。
合計処理時間を件数で割ると、1件あたりの平均時間を計算できます。
各タスクに担当者を割り当ててから、レビューでの役割を決めます。
数値に100を掛けてから割った結果を、入力値と照合します。
ディレクトリにrepositoryを置き、変更のレビューを依頼します。
設定値を定数と呼ぶ理由を、コメントに残します。
エラー時の応答を404に寄せる方針で、レビューを依頼します。
検証コマンドをREADMEに記載します。
READMEを開きます。
baselineをCIと同じ環境で生成します。
handlerからusecaseを呼び出します。
APIを叩き、ログを吐く処理は指摘しません。
ネットワークに繋ぎます。
```

### request-in-condition

「〜てもらえれば」「〜てくれたら」「〜ていただければ」などの依頼を条件節に置き、主節に「が」「は」「も」がない文を検出します。

#### 検出される例

```markdown
設定ファイルを送ってもらえれば、こちらでCIの設定に反映します。
エラーログを貼ってくれたら、発生箇所を調べます。
```

#### 検出されない例

```markdown
CIの設定を確認するため、設定ファイルを送ってほしいです。
設定ファイルを送ってもらえれば、CIが通るか確認できます。
ログを貼ってくれたら、原因はチームで調べます。
手順を書いていただければ、ほかの担当者も試せます。
手順を見せていただければ十分です。
ログを送ってもらえると、発生箇所を調べられます。
```

### calqued-metaphor

構成を説明する比喩として使われた「骨格」「足場」「骨組み」「土台」を検出します。文脈によっては問題ないため、指す内容を確かめてください。

#### 検出される例

```markdown
初期実装では、全サービスの設定ファイルを同じ骨格で作ります。
APIの雛形を用意し、画面の骨格を揃えてから実装します。
このコードを足場にして画面を作ります。
同じ骨組みで四つの仕様を書きます。
このファイルを土台にして機能を追加します。
```

#### 検出されない例

```markdown
初期実装では、全サービスの設定ファイルを同じ構成で作ります。
カメラの映像から骨格推定を行い、関節座標を保存します。
筋電図と骨格筋の動きを照合して、測定結果を確認します。
共通レイアウトを使って画面を作ります。
仕様の章立てを四つの文書で揃えます。
外壁工事の足場を設置します。
HTMLとbodyの骨組みを共通のLayoutで定義します。
ピラミッドの土台を測ります。
```

### foreign-field-term

法律、行政、物流、言語学など、別分野の用語をソフトウェア開発の説明に流用している箇所を検出します。本来の分野で使われている文も検出するため、指す対象と動作を確かめてください。

言語学の用語の「語」は、単体の名詞として使った箇所だけを検出します。前に漢字、カタカナ、数字、英字がある「用語」「日本語」「ドイツ語」「1語」や、後ろに漢字が続く「語句」、動詞の「語る」は検出しません。ただし、「語自体」「語単位」「語同士」は検出します。

#### 検出される例

```markdown

このスクリプトが運用担当者の承認まで行うのは越権です。
このREADMEを設定の正本として扱い、CIでも参照します。
この規則を憲法として扱います。
公開の条件は未決です。
新しい運用方針を布告しました。
質問への追い返しを追加しました。
質問を追い返す。質問を追い返した。
語を選ぶ。
硬い語を避ける。
分野の語を調べる。
表す語がある。
同じ語を使う。
副作用：語の所在を示す。
語自体を確認する。
語単位で数える。
語同士を比べる。
```

#### 検出されない例

```markdown
一つのlint規則に判定条件以外の公開手順まで書いていたため、公開手順を別にしました。
操作が権限外なら、管理者に承認を依頼します。

この規則を最優先のルールとして扱います。
公開の条件はまだ決めていません。
決済は未決済です。申請は未決裁です。
相手には理由を尋ねます。
言葉を選ぶ。
硬い言葉を避ける。
その分野の用語を調べる。
表す言葉がある。
同じ単語を使う。
副作用：該当する箇所を示す。
言葉自体を確認する。
単語単位で数える。
単語同士を比べる。
用語を確認する。
日本語を読む。
ドイツ語を学ぶ。
1語を数える。
語句を確認する。
語った内容を記録する。
「語」を単体で使わない。
`語`を単体で使わない。
```

### physical-verb-for-abstract

抽象的な名詞に物や体の動きを表す動詞を使った「比喩が立ち上がる」「限定が落ちる」などを検出します。「落ちる」は、省略を表す使い方と、「条件は〜に落ちる」の形を対象にします。

#### 検出される例

```markdown
議論の途中で論点が立ち上がるため、会議の記録を更新します。
差分の説明では技術的な限定が落ちるため、適用条件を追記します。
一方の意図が落ちるため、両方を含む文に直しました。
書き直しで落ちた指示を報告しました。
書く側の条件は「判断について書く」に落ちました。
```

#### 検出されない例

```markdown
新しい開発環境が立ち上がるまで、APIの疎通確認を待ちます。
適用条件が書かれていないため、説明に追記します。
一方の意図が文に残らないため、両方を含む文に直しました。
書き直しで削除された指示を報告しました。
条件を「判断について書く」にまとめました。
CIが落ちた理由を調べます。理由はテストが落ちたためです。
非可逆圧縮では情報が落ちます。処理のパフォーマンスが落ちます。
```

### person-word-for-code

コードの識別子と動作がある文で、人を指す「誰が」「誰から」を検出します。

#### 検出される例

```markdown
処理が返す `not_found` は誰が404へ変換していますか。
`config.yaml` の読み込み例外は誰が捕捉して、ログへ記録しますか。
```

#### 検出されない例

```markdown
処理が返す `not_found` は、コード上のどの部分で404へ変換していますか。
このリリースの公開を誰が承認するか、担当者に確認します。
```

### unspecified-behavior

「無言で」「黙って」「静かに」の後にプログラムの動作を表す言葉が続く文を検出します。

#### 検出される例

```markdown
設定ファイルが読めないとき、コマンドは無言で終了します。
重複した申し込みには黙って既存結果を返します。
```

#### 検出されない例

```markdown
設定ファイルが読めないときのコマンドの終了コード、出力内容と出力先は、まだ確認できていません。
レビュアーは作業中、黙って修正内容を確認しました。
リリース担当者が当番から降りる時刻は、運用表で確認します。
```

### vague-evaluative-ending

文末の「効いた」「刺さる」「響く」「効果的です」などの評価や、「効いたのは」などの構文を検出します。

#### 検出される例

```markdown
APIを分離したことで運用が楽になり、この変更が効きました。
APIの利用例に変更した説明が刺さります。
```

#### 検出されない例

```markdown
APIを分離しましたが、運用上の変化はまだ確認できていません。
キャッシュが効き、2回目以降の応答時間が短くなりました。
索引を追加した方法は、この検索条件に有効だと判断しました。
```

### sentence-connection

文頭の「だから」や、文をつなぐダッシュ（`──`、`—`、`―`）を検出します。

#### 検出される例

```markdown
テストの実行時間が短くなった。だからCIに追加します。
設定ファイルは二つあります ── 開発用と本番用です。
```

#### 検出されない例

```markdown
テストの実行時間が短くなったため、CIに追加します。
リリース期限が近いのだから、設定変更の確認を今日中に終えます。
だからといって、すべてのテストをCIから外す必要はありません。
```

## 検査しない範囲

frontmatter、コードブロック、インラインコード、HTMLコメント、`>`で始まる引用行、Markdownの引用ブロックの中は指摘しません。同じ行で閉じる「」『』の中も指摘しません。

各規則の説明に挙げた言葉や表現を含まない文は、不自然な言い回しがあっても検出しません。指摘がないことは、文章全体に問題がないことを意味しません。

## 開発

```sh
npm test
npm run evaluate
```

`test/cases.json`には文章と期待する指摘を組にした評価データがあります。`scripts/evaluate.js`は全件をtextlintで検査し、規則IDと指摘範囲の文字列を照合します。検出漏れか誤検出があれば終了コード1で終わります。
